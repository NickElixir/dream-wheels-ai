# Identity resolve: wheel URL refresh contract

`POST /identity/resolve` supports two multipart modes. Authentication and the
existing `identity_resolve` rate limit apply to both.

## Full identity resolve

Required multipart fields:

| Field | Type | Required |
| --- | --- | --- |
| `car_image` | file | yes |
| `wheel_image` | file | yes |
| `rim_product_url` | text | no |
| `init_data` / existing auth credentials | text/header | as configured |

This is the existing behavior: create an identity draft, normalize and persist
the car and wheel source assets, run vehicle recognition, and return vehicle
and rim proposals. `rim_product_url`, when present, remains a source hint; this
mode does not change its existing compatibility contract.

## Wheel-only refresh of an existing draft

Required multipart fields:

| Field | Type | Required |
| --- | --- | --- |
| `draft_id` | UUID text | yes |
| `rim_product_url` | text | yes |
| `vehicle` | `VehicleCandidate` JSON text | no |
| `vehicle_user_confirmed` | boolean | required as `true` when `vehicle` is supplied |
| `init_data` / existing auth credentials | text/header | as configured |

`car_image` and `wheel_image` must not be sent in this mode. The request must
be authenticated; the draft must belong to that principal, have status
`resolved`, and not be expired. The endpoint resolves the product URL and
image, but does not invoke vehicle recognition/VLM. The recognition result in
`vehicle` is preserved unchanged. An explicitly corrected candidate is stored
separately as `confirmed_vehicle`; it does not replace the original result.

### Response

Both modes return the existing `IdentityResolveResponse` shape:

| Field | Meaning |
| --- | --- |
| `draft_id` | Existing or newly created identity draft |
| `car_asset_id` | Preserved car source asset |
| `rim_asset_id` | Current wheel source asset; replaced after successful URL refresh |
| `vehicle` | Original vehicle recognition result |
| `confirmed_vehicle` | Optional explicit user confirmation/correction |
| `rim` | Editable wheel proposal and source provenance |
| `resolver` | Identity resolver identifier |

`rim` contains `status`, `product_url`, `brand`, `model`, `sku`,
`wheel_diameter_in`, `wheel_width_j`, `bolt_count`, `pcd_mm`,
`center_bore_mm`, `offset_et_mm`, `confidence`, `source`, `revision`,
`source_fingerprint`, `field_candidates`, `conflicts`, `variant_state`, and
`selected_variant_sku`. `field_candidates` and `conflicts` retain resolver
provenance/conflict information. This contract intentionally does not add a
parallel `variants` collection: Create needs to distinguish unresolved
selection from absent specifications, while exposing selectable choices is
not part of this prerequisite.

`variant_state` is one of `none`, `selection_required`, or `selected`.
`selected_variant_sku` is populated when available; a resolver-selected variant
may have no SKU in its source, so `variant_state: "selected"` can coexist with
`selected_variant_sku: null`. `status: "resolved"` means the product source was successfully
parsed; it does not imply that the user has selected an exact commercial
variant. Thus `status: "resolved"` may coexist with
`variant_state: "selection_required"`.

Unavailable or untrusted values remain null/absent; the identity layer does not
fabricate specifications. When multiple variants make exact values ambiguous,
the resolver withholds those values and the identity proposal preserves that
state rather than inferring a wheel.

### Vehicle and revision semantics

The original recognition result (`vehicle`) is never overwritten by wheel-only
refresh. If the request supplies `vehicle` with
`vehicle_user_confirmed=true`, the candidate is stored separately in
`confirmed_vehicle`, subject to the existing confirmation/conflict checks.

On successful refresh, `rim.revision` is the previous rim revision plus one.
It is optimistic concurrency control for editable draft rim state. A stale
concurrent refresh returns `identity_draft_rim_revision_conflict` instead of
overwriting a newer update. The existing car asset remains unchanged. A
successful refresh follows this asset path:

```text
product URL → metadata and image extraction → SSRF-safe image fetch
→ image normalization → new rim_original asset → draft rim_asset_id update
```

Previous assets, render jobs/snapshots, and Fitment history are not deleted or
rewritten by this operation.

### Failures and recovery

Parser/resolution failures are operational source errors, not Fitment verdicts;
they do not produce `unknown` or `incompatible` Fitment results. A failed
refresh leaves the current draft and its asset reference unchanged. The user
can retry with another URL, and manual wheel upload remains available.
Operational error details include `error_code`, `retryable`, and
`manual_fallback` where generated by the wheel-refresh error path.

| Error code | Meaning / recovery |
| --- | --- |
| `rim_source_resolver_disabled` | Resolver feature flag is off; retry after it is enabled. |
| `identity_draft_unavailable` | Missing, foreign, expired, non-resolved, or unusable draft; select a valid owned draft. |
| `invalid_identity_resolve_mode` | Conflicting multipart mode fields; send either the full-resolve or wheel-only field set. |
| `invalid_rim_product_url` | URL failed input validation; correct and retry. |
| `vehicle_confirmation_required` | A supplied vehicle correction was not explicitly confirmed. |
| `invalid_confirmed_vehicle` | Candidate JSON does not match the existing vehicle schema. |
| `identity_draft_vehicle_conflict` | A different confirmed vehicle already exists on the draft. |
| `rim_source_*` | Product source fetch/parse/security failure; retry another URL when appropriate. |
| `rim_source_image_*` | Product image unavailable or could not be safely fetched/normalized; retry another URL or upload manually. |
| `rim_source_asset_upload_failed` | Resolved image could not be stored; retry after storage recovers. |
| `identity_draft_rim_revision_conflict` | A newer wheel update won the race; reload the draft before retrying. |

### Staging prerequisite

Live product URL resolution requires the backend environment setting:

```text
RIM_URL_RESOLVER_ENABLED=true
```

This document does not authorize production deployment or enabling the flag in
production.
