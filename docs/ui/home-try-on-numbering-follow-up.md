# UI-007 — стабильная нумерация примерок в аккаунте

Дата решения: 2026-10-07.
Статус: **реализовано в отдельной ветке, ожидает независимого ревью и staging-приёмки**.
Миграция 0040 подготовлена; на staging/production в рамках реализации не применялась.

## Утверждённая подпись главного экрана

- Если есть подтверждённая пользователем марка/модель автомобиля, показывать её.
- Иначе показывать `Примерка #12` / `Try-on #12`, где 12 — стабильный порядковый номер примерки внутри аккаунта.
- Бренд, модель, артикул и характеристики диска не использовать как fallback названия.
- «Примерка автомобиля» не является выбранным fallback.

23.10.2026 владелец расширил scope отдельного PR на Home, History и Result и утвердил план реализации. Формат вторичной строки даты/времени остаётся отдельным решением.

## Текущее поведение и разница

`src/jobs_api.py` создаёт job_id через `uuid.uuid4()`.
`webapp/app.js: humanRenderTitle` использует подтверждённый vehicle, затем данные диска, затем первые шесть символов job_id.
Эти символы не являются порядковым номером и не отражают последовательность создания.
`#previous-2` в локальном preview был демонстрационным текстом, а не серверным номером.

## Требования к отдельной реализации

1. Назначать и хранить номер на сервере в рамках аккаунта; UUID сохраняется техническим идентификатором.
2. Номер не должен зависеть от позиции в загруженном списке, пагинации, сортировки или фильтров.
3. Одновременное создание и повтор идемпотентного запроса не должны создавать дублирующиеся номера или перенумеровывать существующую примерку.
4. Подготовить миграцию для существующих примерок по порядку создания с детерминированным разрешением одинаковых timestamps.
5. Определить и зафиксировать политику failed/cancelled/deleted jobs и объединения аккаунтов до реализации; не делать скрытых продуктовых предположений. Принятые номера не должны меняться при обычном просмотре истории.
6. Передать номер через необходимые create/history/detail API и использовать его в Home view model без глобальной несогласованной замены shared title helper.
7. Если номера нет, не представлять UUID или индекс страницы как порядковый номер. Политику переходного fallback согласовать в PR.

## Частичная UI-реализация 07.10.2026

Для Home удалён fallback по диску, вторичная строка показывает только календарную дату числом и месяцем (например, 7 октября; без Сегодня/Вчера), без времени и характеристик. История и Result не изменены. До реализации нумерации сохраняется существующий короткий технический ID как временный fallback; это не порядковый номер. В local preview `Примерка #12` — демонстрация целевого вида. Задача серверной нумерации остаётся открытой.

## Утверждённая политика реализации 23.10.2026

- Номер выдаёт PostgreSQL при вставке job и фиксирует вместе с транзакцией. Откат не выдаёт номер. Идемпотентный повтор возвращает номер того же UUID; пока запись ещё не зафиксирована, API возвращает 409 для повтора.
- Все существующие статусы, включая failed/cancelled, участвуют в нумерации. Удалённые номера не используются повторно: счётчик хранится в users отдельно от jobs.
- Backfill: в каждом аккаунте created_at, затем UUID id. Записи без владельца остаются без номера до назначения владельца.
- При объединении выживает более старый аккаунт (created_at, id). Его номера сохраняются, примерки второго аккаунта получают следующие номера в порядке created_at, id. UUID и ссылки сохраняются.
- API create/history/detail/status передают try_on_number. Пользовательские заголовки Home/History/Result используют подтверждённую модель автомобиля или локализованное «Примерка #N»; при отсутствии номера — «Примерка» без UUID и без модели диска.
- Общий legacy humanRenderTitle не заменяется глобально. Номер не является ключом доступа или частью маршрута.

Локальная браузерная проверка: tests/browser-fixtures/try-on-numbering.html (RU/EN, три экрана, подтверждённая модель, отсутствие номера, пять redraw History/Result). Это управляемые данные, не staging E2E.
