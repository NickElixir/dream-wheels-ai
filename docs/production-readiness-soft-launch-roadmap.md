# Dream Wheels AI — Production Readiness & Soft Launch Roadmap

**Статус:** рабочий план команды  
**Дата актуализации:** 6 августа 2026  
**Цель:** безопасно вывести основную виртуальную примерку в production, начать управляемый soft launch и параллельно подготовить развитие AI-пайплайна без смешивания нескольких крупных рисков в одном релизе.

---

## 1. Краткое решение

Полный перенос текущего состояния `staging` в production одним merge пока не рекомендуется.

Допустим **условный запуск основного пользовательского сценария**, если до релиза закрыты критические задачи по веткам, CI, конфигурации окружений, миграциям и платежному сценарию.

Рекомендуемый объём первого production-релиза:

- виртуальная примерка дисков;
- авторизация и кабинет;
- баланс, списание рендеров и пополнение;
- история результатов;
- сохранение исходных и сгенерированных изображений;
- сбор обратной связи.

Функции, которые не должны блокировать основной запуск:

- парсинг характеристик диска по URL;
- автоматическая проверка технической совместимости;
- экспериментальное распознавание автомобиля через VLM;
- автоматическая смена основного генеративного провайдера.

На первом этапе эти функции следует оставить выключенными feature flags, ограничить внутренним тестированием или запустить как отдельную beta-функциональность.

---

## 2. Почему нельзя объединять всё в один релиз

Необходимо разделить три независимых направления:

1. **Production-релиз текущего продукта.**
2. **Стабилизация парсера и проверки совместимости.**
3. **Изменение AI-пайплайна и переход на Wan2.7.**

Если выпустить их одновременно, при ухудшении результата будет трудно определить источник проблемы:

- frontend или backend;
- миграции или конфигурация окружения;
- биллинг или кредитный ledger;
- новый генеративный провайдер;
- входная оценка изображений;
- постобработка;
- парсер характеристик;
- правила проверки совместимости.

Принцип релиза:

> Один этап должен изменять минимально необходимое количество критических компонентов и иметь измеримый результат.

---

## 3. Текущее состояние репозитория

На момент составления плана:

- основная ветка — `main`;
- рабочая ветка перед релизом — `staging`;
- ветки `main` и `staging` разошлись и содержат изменения с обеих сторон;
- CI настроен не на фактический release flow и не выполняет полноценную проверку каждого изменения в `staging`;
- staging-конфигурация frontend содержит привязку к staging backend;
- часть environment-specific конфигурации находится в репозитории;
- парсер URL дисков остаётся нестабильным для сайтов с JavaScript, антибот-защитой и нестандартной разметкой;
- проверка совместимости уже архитектурно отделена от визуальной примерки и может быть отключена;
- текущий генеративный клиент напрямую связан с одним провайдером, поэтому безопасная смена модели требует provider abstraction и воспроизводимого benchmark.

Связанные материалы:

- `docs/ai-rendering-pipeline.md`;
- `docs/fitment-compatibility.md`;
- `docs/fitment-api-contract-v1.md`;
- `.github/workflows/ci.yml`;
- `webapp/vercel.json`;
- `src/rim_url_resolver.py`;
- `src/reve_client.py`.

# Этап 1. Production readiness

## 4. P0 — обязательные задачи до production

### 4.1. Зафиксировать release scope

До подготовки релиза команда должна прекратить добавление необязательных UI-изменений в текущий release candidate.

В релиз входят только:

- исправления критических ошибок;
- безопасность;
- биллинг;
- корректность данных;
- стабильность основного рендера;
- необходимые production-конфигурации;
- аналитика базовой воронки.

Новые улучшения интерфейса и AI-функции переносятся в следующие итерации.

### 4.2. Исправить CI для реального branch flow

CI должен выполняться:

- при каждом push в `staging`;
- для pull request в `staging`;
- для release pull request из `staging` в `main`.

Минимальная конфигурация:

```yaml
on:
  pull_request:
    branches: [main, staging]
  push:
    branches: [staging]
```

Обязательные проверки:

- unit tests;
- integration tests;
- линтер и форматирование;
- проверка импортов и запуска приложения;
- проверка миграций;
- тесты биллинга и возврата зарезервированных рендеров;
- frontend smoke test, если он поддерживается текущей инфраструктурой.

### 4.3. Синхронизировать `main` и `staging`

Нельзя переносить `staging` в `main`, пока ветки содержат независимые пересекающиеся изменения.

Порядок:

1. Создать резервную release-ветку от актуального `staging`.
2. Влить `main` в `staging`.
3. Вручную разрешить конфликты в биллинге, авторизации, конфигурации и webapp.
4. Запустить полный набор тестов.
5. Провести ручной smoke test на staging.
6. Только после этого создать новый release PR `staging -> main`.

### 4.4. Разделить конфигурации staging и production

Общая версия `webapp/vercel.json` не должна жёстко направлять production frontend в staging backend.

Рекомендуемая схема:

- использовать переменную окружения `BACKEND_URL`;
- задать отдельное значение в Vercel project для staging;
- задать отдельное значение для production;
- не хранить environment-specific Vercel project binding как общую конфигурацию продукта;
- проверить, что preview deployment не использует production backend без явного решения.

Критерий готовности:

- production frontend всегда обращается к production backend;
- staging frontend всегда обращается к staging backend;
- переключение определяется окружением, а не ручной правкой общего файла перед релизом.

### 4.5. Проверить миграции базы данных

Перед релизом необходимо провести аудит миграций, добавленных после текущего состояния production.

Проверить:

- порядок применения;
- повторный запуск;
- совместимость со старой версией приложения во время deployment;
- значения по умолчанию;
- ограничения и индексы;
- RLS и доступ сервисных ролей;
- сохранение существующих балансов и платежей;
- стратегию forward-fix при частично применённой миграции.

Перед production:

1. Создать актуальную резервную копию.
2. Применить миграции на копии production-данных или максимально близком staging dataset.
3. Запустить smoke test после миграций.
4. Зафиксировать ответственного за принятие решения о продолжении deployment.

### 4.6. Закрыть критический E2E-сценарий

Обязательный успешный сценарий:

1. Пользователь входит в приложение.
2. Получает стартовый баланс, если он предусмотрен.
3. Загружает фото автомобиля и диска.
4. Frontend корректно показывает состояние загрузки.
5. Создаётся render job.
6. Рендер резервируется или списывается по принятой модели ledger.
7. Провайдер возвращает изображение.
8. Результат сохраняется.
9. Пользователь открывает результат и историю.
10. Исходные и итоговые assets доступны повторно.
11. Пользователь отправляет обратную связь.
12. Повторный рендер не создаёт двойного списания.

Обязательный сценарий ошибки:

1. Рендер зарезервирован.
2. Провайдер завершает запрос ошибкой или timeout.
3. Резерв снимается или баланс восстанавливается.
4. В ledger нет двойной операции.
5. Пользователь получает понятный статус.
6. Повторная попытка создаёт отдельную корректную операцию.

### 4.7. Проверить платежи

До production необходимо подтвердить:

- создание платежа;
- возврат пользователя после оплаты;
- обработку callback/webhook;
- идемпотентность повторного callback;
- начисление правильного количества рендеров;
- отсутствие повторного начисления;
- корректное отображение статуса счёта;
- обработку отменённой и неуспешной оплаты;
- журналирование без утечки секретов и персональных данных.

## 5. Feature flags первого релиза

Рекомендуемая production-конфигурация:

| Функция | Состояние | Комментарий |
|---|---:|---|
| Основная виртуальная примерка | ON | Главный пользовательский сценарий |
| Авторизация и кабинет | ON | Обязательная часть продукта |
| Баланс и платежи | ON | После полного E2E-теста |
| История рендеров | ON | Нужна для возврата пользователя |
| Обратная связь | ON | Нужна для оценки качества |
| Парсер диска по URL | OFF | Не должен блокировать ручную загрузку |
| Fitment verdict | OFF / beta | Отдельная техническая функция |
| Vehicle VLM | OFF / internal | До оценки точности и стоимости |
| Wan2.7 как основной провайдер | OFF | Сначала shadow benchmark |
| Автоматическая генеративная постобработка | OFF | Только после классификации ошибок |

## 6. Release gate

Релиз разрешён только при выполнении всех условий:

- [ ] `main` синхронизирован со `staging`;
- [ ] конфликты разрешены и проверены;
- [ ] CI выполняется для `staging` и release PR;
- [ ] все обязательные тесты зелёные;
- [ ] production frontend не связан со staging backend;
- [ ] миграции проверены на близком к production окружении;
- [ ] успешный render flow пройден вручную;
- [ ] failure/refund flow пройден вручную;
- [ ] платежный flow пройден вручную;
- [ ] feature flags выставлены согласно release scope;
- [ ] настроены error tracking и базовые продуктовые события;
- [ ] назначен ответственный за go/no-go;
- [ ] определён сценарий rollback или forward-fix.

При невыполнении хотя бы одного критического пункта release gate решение — **NO-GO**.

# Этап 2. Controlled soft launch

## 7. Формат запуска

После production deployment не следует сразу масштабировать платный трафик.

Рекомендуемый порядок:

1. Внутренняя проверка production командой.
2. Ограниченная группа знакомых пользователей и партнёров.
3. Прямые приглашения продавцам дисков и автомобилей.
4. Органический контент и демонстрации.
5. Небольшие рекламные тесты только после подтверждения стабильности воронки.
6. Постепенное увеличение трафика при сохранении качества и экономики.

Первые пользователи должны восприниматься не только как клиенты, но и как источник размеченных реальных кейсов для AI evaluation.

## 8. Аналитика soft launch

Минимальные события:

- `upload_started`;
- `upload_completed`;
- `render_started`;
- `render_completed`;
- `render_failed`;
- `result_opened`;
- `feedback_submitted`;
- `repeat_render_started`;
- `payment_started`;
- `payment_completed`.

Минимальные метрики:

| Метрика | Что показывает |
|---|---|
| Upload completion rate | Насколько понятна и стабильна загрузка |
| Upload-to-render conversion | Доходит ли пользователь до основной ценности |
| Render success rate | Техническая стабильность генерации |
| Median/P95 render time | Скорость и хвост задержек |
| Cost per successful render | Экономика AI-пайплайна |
| Positive feedback rate | Воспринимаемое качество |
| Причины отрицательной оценки | Классы ошибок для развития модели |
| Repeat render rate | Полезность и вовлечённость |
| Payment conversion | Готовность платить |
| Refund/recovery rate | Надёжность провайдера и ledger |

Решение о масштабировании маркетинга принимается на основе этих метрик, а не только общего числа регистраций.

# Этап 3. Стабилизация parser и fitment

## 9. Парсер характеристик диска

Парсер URL не должен быть обязательным входом для создания виртуальной примерки.

Рекомендуемый UX:

- пользователь может загрузить фото диска вручную;
- URL — дополнительный способ предзаполнить данные;
- при ошибке парсера пользователь продолжает сценарий вручную;
- распознанные характеристики всегда доступны для проверки и исправления;
- источник каждого поля сохраняется: URL, каталог, ручной ввод или модель.

Порядок развития:

1. Влить и актуализировать fallback-парсинг характеристик из URL path.
2. Создать набор реальных URL разных магазинов.
3. Разделить ошибки на категории:
   - блокировка/anti-bot;
   - JavaScript-only content;
   - отсутствующая structured data;
   - нестандартное название;
   - неоднозначные единицы;
   - неполный набор характеристик.
4. Ввести confidence для каждого извлечённого поля.
5. Не выводить технический verdict при недостаточных данных.
6. Добавить ручную корректировку.
7. Запускать как beta после достижения заданной точности на фиксированном test set.

## 10. Проверка совместимости

Визуальная примерка и техническая совместимость — разные продукты.

Правила:

- совместимость нельзя определять только по изображению;
- недостаток данных должен возвращать `unknown`, а не предположение;
- verdict должен содержать причины и проверенные параметры;
- данные автомобиля и диска должны иметь источник и confidence;
- правила должны быть детерминированными и покрываться тестами;
- beta-версия не должна формулировать результат как гарантию установки.

Рекомендуемый запуск:

1. Internal mode.
2. Invite-only beta.
3. Сбор расхождений с ручной проверкой.
4. Расширение покрытия моделей автомобилей и форматов дисков.
5. Публичный запуск только после оценки precision/recall по размеченному набору.

# Этап 4. Развитие AI-пайплайна

## 11. Сначала — provider abstraction

До переключения на Wan2.7 необходимо убрать прямую зависимость бизнес-логики от конкретного API.

Предлагаемый интерфейс:

```python
class GenerationProvider(Protocol):
    async def generate(self, plan: RenderPlan) -> GenerationResult:
        ...
```

`RenderPlan` должен содержать:

- ссылки или идентификаторы входных изображений;
- задачу редактирования;
- маски и области интереса, если используются;
- ограничения на сохранение автомобиля;
- требования к геометрии колёс;
- параметры качества и разрешения;
- seed или другие параметры воспроизводимости, если поддерживаются;
- версию prompt template;
- версию preprocessing;
- выбранного провайдера и модель.

`GenerationResult` должен содержать:

- итоговый asset;
- provider/model/version;
- latency;
- стоимость;
- статус и тип ошибки;
- moderation/safety status;
- параметры генерации;
- результаты автоматической оценки.

## 12. Переход на Wan2.7

Wan2.7 следует сначала использовать как challenger, а не немедленно заменять текущего провайдера.

Схема:

- текущий провайдер — control;
- Wan2.7 — challenger;
- одинаковые входные кейсы;
- одинаковые критерии оценки;
- versioned prompt templates;
- сохранение всех результатов и метаданных;
- слепая ручная оценка без указания модели.

Критерии сравнения:

- сохранение марки, модели, формы и цвета автомобиля;
- сходство установленного диска с референсом;
- корректное количество колёс;
- положение и масштаб дисков;
- сохранение шин и арок;
- отсутствие деформаций кузова;
- отсутствие лишних объектов и артефактов;
- качество мелких деталей;
- стабильность на сложных ракурсах;
- latency;
- failure rate;
- стоимость успешного результата;
- доля случаев, требующих повторной генерации;
- человеческое предпочтение результата.

Условие переключения:

> Wan2.7 становится основным провайдером только после подтверждённого выигрыша на versioned benchmark и ограниченном production canary.

## 13. Предварительная оценка исходных фото

Оценка входа должна быть каскадной, чтобы не запускать дорогую модель для каждого изображения.

Рекомендуемый pipeline:

1. **Техническая валидация**
   - формат;
   - размер файла;
   - разрешение;
   - повреждённый файл;
   - прозрачность;
   - ориентация.

2. **Недорогие CV-проверки**
   - blur;
   - яркость и контраст;
   - пересвет и недоэкспонирование;
   - доля пустого фона;
   - слишком маленький объект.

3. **Object/geometry checks**
   - наличие автомобиля;
   - наличие видимых колёс;
   - колёса не обрезаны;
   - автомобиль не слишком мал;
   - диск показан с подходящего ракурса;
   - отсутствие нескольких конфликтующих объектов.

4. **VLM только для неоднозначных случаев**
   - пригодность изображения;
   - объяснение проблемы;
   - рекомендация пользователю;
   - классификация причины отказа.

Предлагаемый результат:

```python
class InputAssessment:
    decision: Literal["accept", "warn", "reject"]
    issues: list[str]
    metrics: dict[str, float]
    recommendations: list[str]
    model_versions: dict[str, str]
```

Первый production-режим — **warn-only**. Жёсткий reject включается только для объективно непригодных файлов после анализа false reject rate.

## 14. Автоматическая оценка результата

После генерации должна выполняться проверка результата до показа пользователю.

Проверки:

- изображение успешно декодируется;
- разрешение соответствует требованиям;
- автомобиль сохранён;
- количество и положение колёс корректны;
- диски похожи на референс;
- отсутствуют крупные деформации;
- нет очевидных артефактов;
- результат не является почти полной копией исходника без замены дисков;
- нет moderation/safety ошибки.

Решение validator:

- `accept` — показать результат;
- `retry` — выполнить одну внутреннюю повторную генерацию без повторного списания пользователя;
- `fail` — вернуть контролируемую ошибку и восстановить баланс согласно правилам ledger.

Повторные попытки должны быть ограничены, чтобы не создавать неконтролируемый расход.

## 15. Постобработка

Не следует добавлять универсальную генеративную постобработку сразу после основной модели.

Сначала необходимо определить конкретные повторяющиеся классы дефектов, например:

- низкое разрешение;
- локальные артефакты на диске;
- повреждение номерного знака;
- небольшие дефекты вокруг арки;
- цветовой сдвиг;
- несогласованная резкость.

Для каждого класса выбирается отдельный инструмент:

- обычный resize/upscale;
- sharpening или denoise;
- локальный inpainting по маске;
- восстановление конкретной области;
- повторная основная генерация.

Постобработка принимается только после проверки, что она не ухудшает идентичность автомобиля и сходство диска.

# Приоритеты

## 16. Очерёдность работ

### P0 — до production

1. Заморозить release scope.
2. Исправить CI для `staging`.
3. Синхронизировать `main` и `staging`.
4. Разделить staging/production конфигурации.
5. Проверить миграции.
6. Пройти render, failure/refund и payment E2E.
7. Настроить feature flags.
8. Подготовить новый release PR.
9. Выполнить production canary и принять go/no-go.

### P1 — сразу после запуска

1. Настроить продуктовую аналитику и dashboard.
2. Запустить ограниченный soft launch.
3. Создать versioned AI evaluation dataset.
4. Ввести `GenerationProvider` и `RenderPlan`.
5. Подключить Wan2.7 в shadow/benchmark mode.
6. Добавить warn-only оценку входных изображений.
7. Добавить базовый output validator и один бесплатный internal retry.

### P2 — после получения реальных данных

1. Улучшать parser по измеренным классам ошибок.
2. Запустить fitment invite-only beta.
3. Добавить targeted postprocessing.
4. Провести production A/B или canary Wan2.7.
5. Масштабировать маркетинг.
6. Расширять каталог кейсов и regression dataset.

## 18. Definition of Done для soft launch

Soft launch считается успешно начатым, когда:

- основной production flow стабилен;
- пользователи могут самостоятельно пройти путь от загрузки до результата;
- ошибки генерации не приводят к потере оплаченного баланса;
- доступны история и обратная связь;
- команда видит базовую воронку и технические ошибки;
- parser и fitment не блокируют виртуальную примерку;
- AI-провайдер можно менять через абстракцию, а не переписывание бизнес-логики;
- создан baseline dataset для дальнейшего сравнения моделей;
- маркетинговый трафик увеличивается постепенно и контролируемо.

---

## 19. Главное правило следующего этапа

> Сначала выпустить и измерить стабильный core product. Затем отдельно улучшать качество AI, parser и fitment на основании реальных данных.

Это позволяет одновременно начать маркетинг, не задерживая продукт из-за экспериментальных функций, и создать корректную основу для перехода на Wan2.7, предварительной оценки фото и автоматической проверки результатов.
